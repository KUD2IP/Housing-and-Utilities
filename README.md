# Контур — прогноз тепла группы домов

Учебный контур для дисциплины «Проектный практикум», тема 5 «Жилищно-коммунальное хозяйство».
Диспетчер управляющей компании видит, сколько тепла закупить на неделю, насколько прогнозу можно верить и почему модель дала именно такую цифру.

Пользовательская величина — гигакалории и рубли по тарифу из `config/pipeline.yaml` (в проекте 2 500 ₽/Гкал, тариф учебный).

## Как запустить

Нужны JDK 21, Maven, Python 3.11 и Node.js.

```bash
./scripts/run.sh
```

Скрипт собирает интерфейс, ставит зависимости Python, заново генерирует источники и поднимает сервис.
После строки `Контур: http://localhost:8080` откройте этот адрес.

Повторный запуск не обучает модель заново: если в базе уже есть рабочая версия, сервис только досчитывает новые сутки.

## Что делает система

1. Собирает четыре источника. Структурированный архив погоды, полуструктурированные журналы приборов и тексты диспетчера, паспорта домов с координатами. Отдельно запрашивает последние 14 суток Open-Meteo и кладёт их в сверку, не в обучение.
2. Ведёт журнал загрузок. Повтор того же файла пропускается по контрольной сумме, повтор той же строки не вставляется. Битая строка отклоняется, сервис при этом не падает.
3. Чистит показания только по прошлому (выброс датчика и короткий пропуск), строит признаки и проверяет, что будущая цель не протекает в прошлые признаки.
4. Сравнивает три модели разных классов на одном временном разрезе: сезонный наивный прогноз, гребневую регрессию и градиентный бустинг. Поиск гиперпараметров ограничен бюджетом. Отложенный отрезок в подборе не участвует.
5. Показывает закупку, сравнение моделей, вклад признаков, сдвиг распределения и журнал опытов.

## Архитектура

```text
архив погоды CSV ─┐
журналы ПУ .log  ─┼─ Java, сбор и журнал ─ SQLite ─ Python, признаки и модели ─ та же SQLite
тексты диспетчера─┤                                              │
паспорта JSON    ─┘                                              ▼
Open-Meteo (только сверка)                              React, панель диспетчера
                                                         Spring отдаёт её и API
```

Java отвечает за приём данных, версии моделей, откат и HTTP. Python отвечает за признаки, обучение, объяснения и мониторинг: для временного разреза, бустинга и вкладов признаков это прямой инструмент, а не обходной. Одна база на обоих контурах, чтобы не плодить копии. Интерфейс свой, на React, без отдельной BI-системы: вопрос диспетчера узкий, и экран собран под него.

Миграции лежат по одной на таблицу в `src/main/resources/db/migration`. У актуальной ветки Flyway нет модуля SQLite, поэтому версии применяет `DatabaseMigrations`: каждая `V*.sql` один раз, номер пишется в `schema_migrations`.

## Откуда данные

Погода Москвы с 2023-01-01 — архив Open-Meteo (CC BY 4.0), файл `data/cache/open_meteo.json`.
Потребление, журналы приборов и тексты инцидентов синтетические и согласованы с этой погодой, зерно 42. Персональных данных нет.
Исходная партия — всё до 2026-11-11, дельта — с этой даты. Кнопка «Догрузить новую партию» на экране «Данные» берёт дельту. Второй запуск тех же файлов добавляет 0 строк.

В архиве специально есть битая строка погоды и строки журнала, которые сервис отклоняет. Это видно в журнале загрузок со статусом PARTIAL.

## Как устроено сравнение моделей

Даты режутся один раз, 70 / 15 / 15, и этот разрез общий для всех домов. Зерно 42.
Модель выбирается по проверочному отрезку, цифра для диспетчера — ошибка на отложенном.
Бюджет поиска — 12 конфигураций (4 значения alpha у регрессии и 8 у бустинга). Наивная модель в бюджет не входит: это база для сравнения.
Новая версия становится рабочей, только если на своём отложенном отрезке она лучше текущей хотя бы на 2% и этот отрезок целиком позже обучения обеих. Иначе она остаётся кандидатом. Кандидата можно вывести вручную, архивную версию — вернуть.

## Экраны

| Экран | Вопрос |
| --- | --- |
| Закупка | Сколько гигакалорий купить на 7 суток и какой запас заложить |
| Модели | Какая модель точнее на отложенном отрезке, в гигакалориях и рублях |
| Почему так | Из чего сложился прогноз конкретного дома и дня |
| Качество | Разъехались ли данные с тем же сезоном обучения и выросла ли ошибка |
| Опыты | Какой поиск уже сделан и повторяется ли он по номеру |
| Данные | Что загружено, что отбраковано, что лежит только в сверке |

## Сценарий показа

1. «Закупка»: сумма недели, запас в размере отложенной MAE и перевод в рубли.
2. «Модели»: наивный прогноз, регрессия и бустинг в одной таблице. Рабочая строка выделена.
3. «Почему так»: любой дом и дата. Два независимых способа важности и график зависимости от градусо-суток.
4. «Опыты»: «Повторить» у любой строки. MAE должна совпасть с журналом.
5. «Данные»: первая партия со статусом PARTIAL, внешние 14 суток отдельно. «Догрузить новую партию» дважды: сначала новые строки, затем нули.
6. «Качество»: «Смоделировать сдвиг» включает рекомендацию переобучения, не портя факты. «Переобучить» на тех же данных оставляет новую версию кандидатом, потому что отложенная ошибка не улучшилась на 2%.

## Ограничения, которые стоит проговорить

Погода дня, на который строится прогноз, считается известной заранее: диспетчер видит прогноз погоды. На истории в проверку подставлена фактическая погода, поэтому отложенная ошибка немного оптимистична.
Проверочный отрезок использован и для отбора признаков, и для поиска гиперпараметров, поэтому его метрика у победителя чуть лучше, чем была бы на совсем нетронутых данных. Для решения берётся отложенный отрезок.
Инцидент текущего дня в признаки не входит. Выброс датчика исключается из цели, реальное отключение остаётся.
Потребление синтетическое. Тариф в конфигурации учебный.
